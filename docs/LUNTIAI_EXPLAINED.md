# LuntiAI: dataset, prediction, and explanation guide

Prepared for Joseph D. Alejo · CS 24/L — Explainable AI · November 8, 2026

## A short explanation you can say aloud

“LuntiAI began as our Technopreneurship crop-recommendation prototype for Tagum
City. For Explainable AI, I use its saved Random Forest and explain the model's
crop scores with TreeSHAP. The dataset contains 120,000 synthetic rows generated
from hand-coded profiles for twelve crops. Each row has eight numeric soil and
weather inputs. The model achieved 85.62% accuracy on a held-out synthetic test
split. That measures recovery of generated crop labels, not success on farms.
The website sends the eight form values to FastAPI on Hugging Face Spaces. The
server runs the saved model and returns probabilities plus all eight signed SHAP
contributions. I also compare model-agnostic KernelSHAP in the notebook and check
that the explanations reconstruct the model scores. Soil and rainfall presets,
assumed crop ranges, and lack of field validation are the main limitations.”

## Which dataset is used?

The actual training file is [`data/philippine_crop_dataset.csv`](../data/philippine_crop_dataset.csv).
It is generated by [`data/generate_dataset.py`](../data/generate_dataset.py).
It is not a verified set of 120,000 Philippine farm observations, and the source
does not establish it as a downloaded Kaggle dataset.

| Property | Verified implementation |
|---|---|
| Rows | 120,000 |
| Inputs | 8 numeric columns |
| Target | `label`, one of 12 crop names |
| Random seed | 42 |
| Missing cells / duplicate rows | 0 / 0 in the notebook audit |
| Training / test | Stratified 80:20 split: 96,000 / 24,000 rows, seed 42 |
| Labels mean | The crop profile that generated each row |
| Labels do not mean | Observed best crop, yield, profit, or actual farm success |

| Crop | Generated rows |
|---|---:|
| Rice, Banana, Coconut | 12,000 each |
| Cacao, Durian | 11,000 each |
| Corn | 10,000 |
| Mango, Papaya, Cassava, Sweet Potato | 9,000 each |
| Eggplant, Tomato | 8,000 each |

For each crop, `CROP_PROFILES` supplies a minimum, maximum, mean, and standard
deviation for each feature. The generator samples normal values, clips them to
the specified bounds, and adds small jitter at boundaries. The helper is named
`truncated_normal`, but the implementation is **clipping**, not a mathematically
truncated-normal sampler. It imposes a rainfall–pH relationship and a
temperature–humidity relationship, multiplies rainfall by sampled seasonal
factors, rounds values, attaches the crop label, and shuffles the rows.

These imposed relationships and crop profiles are assumptions. They explain why
the data look structured; they do not constitute measurements of those
relationships in Tagum. Train and test rows share the same generator, so the
test evaluates generalization within that synthetic setup.

## Where did the numeric assumptions come from?

[`data/sources.md`](../data/sources.md) and generator comments record the original
references, including PhilRice, DA Region XI, Yara Philippines, TADECO/Hijo,
ACDI/VOCA, ICRAF, PCA, UPLB, PCARRD/PCAARRD, PhilRootcrops/VSU, BSWM, and PAGASA.
They are broad source claims. A citation to an institution does not verify each
mean, range, correlation, or label. The current project lacks a complete
source-table-to-parameter audit trail.

In particular, some nutrient references discuss fertilizer application in kg/ha,
while model inputs are labeled soil concentration in mg/kg. Those quantities
cannot be substituted directly. Converting them requires soil mass/depth,
bulk density, nutrient form, and other assumptions. Field sampling, comparable
lab methods, and documented unit calibration are needed before agricultural use.

Do not say “the dataset was collected by PAGASA/BSWM” or “soil estimates are
accurate within ±15–20%.” Neither claim is established by this repository.

## Where do website inputs come from?

The exact model feature order is:

`N, P, K, temperature, humidity, ph, rainfall, OM`

| Input | App unit | Default source |
|---|---|---|
| N, P, K | mg/kg | Hard-coded barangay soil profile |
| temperature | °C | OpenWeatherMap when available; otherwise monthly preset |
| humidity | % | OpenWeatherMap when available; otherwise monthly preset |
| ph | pH scale | Hard-coded barangay soil profile |
| rainfall | mm/month | Monthly climate preset, including when weather API is live |
| OM | % soil weight | Hard-coded barangay soil profile |

All eight form values are editable. Selecting a barangay looks up one of 23
profiles in [`api/barangay_data.py`](../api/barangay_data.py); it does not read a
soil sensor or that user's laboratory record. The barangay name is not a ninth
model feature. It is used for defaults and related display information.

[`api/weather_service.py`](../api/weather_service.py) optionally calls
OpenWeatherMap for current temperature and humidity. Its current one-hour rain
value is separate from the monthly rainfall used by the model. A one-hour
measurement must not be relabeled as mm/month. If the API is unavailable, the
service returns labeled monthly presets. The original comments attribute these
presets to PAGASA 1991–2020 Davao normals; the exact matching source table has not
been independently verified. Current weather and monthly climate represent
different time scales, another deployment limitation.

Changing the form changes that prediction only. It does not edit the training
CSV or retrain the model. SHAP explains the numbers actually submitted, even
when they differ from the sidebar's original defaults.

## Where does inference happen?

```text
Browser: editable form with 8 numbers
    → POST /predict, authenticated request
    → FastAPI on Hugging Face Spaces (or your local Python server)
    → saved crop_model.pkl + label_encoder.pkl
    → Random Forest predict / predict_proba
    → TreeSHAP on the same model and same ordered input
    → JSON containing crop scores, complete explanation, and rule-based extras
    → browser displays scores and signed explanation bars
```

GitHub stores source code. Hugging Face's Docker Space hosts both the frontend
and API on the same origin. The container listens on port 7860; the local
launcher uses 8000. The frontend uses its current origin for API requests.
The server loads the saved model at startup. It does not train it on each click.
No language model or ChatGPT generates the crop classification.

Training is separate: [`train_model.py`](../train_model.py) reads the CSV,
encodes labels, splits data, fits the Random Forest, evaluates it, and saves
artifacts in `model/`. Running it can replace those artifacts. Normal app use
only loads them.

## Why this model and these XAI methods?

The existing Random Forest uses 200 trees, maximum depth 25, minimum split size
5, minimum leaf size 2, square-root feature selection, balanced class weights,
and random state 42. This reuses the project's existing classifier and handles
nonlinear interactions in numeric tabular inputs without requiring scaling.
These are inherited settings, not a documented optimal hyperparameter search.

The notebook supplies concrete comparisons rather than claiming the model is
universally best:

| Model | Synthetic test accuracy | Macro F1 |
|---|---:|---:|
| Majority-class baseline | 10.00% | 0.0152 |
| Depth-4 decision tree | 57.43% | 0.5436 |
| Existing Random Forest configuration | 85.62% | 0.8493 |

Macro F1 gives each crop equal weight. Accuracy alone can hide poorer results
for an individual crop; the per-class report and confusion matrix are saved in
[`reports/xai/`](../reports/xai/). The comparisons do not establish field
performance or probability calibration.

| XAI dimension | Deployed TreeSHAP | Notebook KernelSHAP comparison |
|---|---|---|
| Model dependence / agnosticity | Model-specific: uses tree structure | Model-agnostic: queries a prediction function |
| Timing | Post-hoc, after model training | Post-hoc |
| Data type | Numerical tabular inputs | Same numerical tabular inputs |
| Primary scope | Local, one row and one crop class | Local, one diagnostic case |
| Explanation type | Signed feature attribution | Signed feature attribution |
| Output explained | Random Forest class probability | Same model's class probability |
| Reference convention | Training path counts, `tree_path_dependent` | 24 selected training-background rows |
| Global use | Aggregate absolute values over a 120-case balanced sample | Not used as a global study here |
| Deployment | API and website | Notebook only |

SHAP is a framework with different algorithms. It is incorrect to call the
deployed TreeSHAP implementation model-agnostic merely because KernelSHAP is.
The tree method is a practical fit for this saved forest; KernelSHAP provides a
black-box comparison but requires repeated model queries. Their background
conventions differ, so different attributions are not automatically errors.

`model_output="raw"` is the SHAP API setting here. For this scikit-learn
RandomForestClassifier, the outputs being reconstructed are class
probabilities, not logits. That interpretation is verified against
`predict_proba`, not inferred from the parameter name alone.

## How to explain a SHAP result

For a chosen class, the required identity is:

`baseline + sum(all eight signed contributions) = predicted class probability`

A positive contribution raises that class's score relative to its baseline; a
negative contribution lowers it. The baseline comes from the explainer's
reference convention. It is not zero and is not a farmer's expected success
rate. The app displays contributions in percentage points. Explaining only the
largest positive terms would omit evidence needed to reconstruct the score.

For the stored demonstration input:

```text
N=131.3, P=44.1, K=120.5, temperature=28.22,
humidity=81.6, ph=5.42, rainfall=199.36, OM=4.38
```

The saved model gives Banana approximately **99.21%**. Its baseline is about
**8.33%**. Nitrogen contributes about **+31.35 percentage points**, potassium
**+17.77**, and rainfall **+13.38**; the remaining five terms are also included
in the complete explanation. These describe how the model scored this row.
They do not prove that adding nitrogen will increase real banana yield.

The runner-up view explains a different quantity: the score gap between the
winning crop and the second-ranked crop. For every feature it subtracts the
runner-up attribution from the winner's attribution, and does the same for
their baselines. Those differences reconstruct the probability gap. This is a
class-score contrast, not a feasible counterfactual farming plan.

## What was checked, and what failed?

The executed [`notebooks/LuntiAI_ML_and_XAI.ipynb`](../notebooks/LuntiAI_ML_and_XAI.ipynb)
contains the ML pipeline, baselines, plots, local/global explanations, reference
comparison, and limitations. Its shared app helper is
[`api/xai.py`](../api/xai.py). Results are recorded in
[`reports/xai/evaluation.json`](../reports/xai/evaluation.json).

- Reconstructed saved-model probabilities after retraining: maximum difference
  about `3.33e-16`.
- Path-dependent TreeSHAP: 120 held-out cases, ten random cases per true crop;
  attribution tensor `120 × 8 × 12`; maximum reconstruction residual
  `5.67e-14`, below the `1e-5` tolerance.
- Global attribution ranking: K, N, rainfall, humidity, OM, P, temperature, pH.
  Half-sample rank Spearman correlation was approximately 0.976. This is one
  descriptive stability diagnostic on a small balanced sample, not a population
  estimate, a confidence interval, or evidence of causal importance.
- KernelSHAP: one case, 24 training-background rows, all 254 nontrivial feature
  coalitions; reconstruction residual about `1.11e-16`.
- **Experimental interventional TreeSHAP failed** the selected tolerance in
  this pinned environment: maximum residual about `0.001394`. It is documented
  as a failed numerical check and is excluded from the app. Its attributions
  must not be presented as a validated replacement for the deployed method.

Reconstruction checks test numerical consistency with a model output. They do
not establish that the model is correct, causal, fair, robust to distribution
shift, or agriculturally safe. Correlated features and the reference convention
affect attribution. A high model score can still arise for unrealistic input.

## What is machine learning and what is a rule?

| Feature | Implementation |
|---|---|
| Crop class and probability ranking | Saved Random Forest |
| Why a crop score rose or fell | TreeSHAP on that forest |
| Soil defaults | Hard-coded barangay lookup |
| Weather defaults | Optional external weather API plus monthly presets |
| Fertilizer, maturity, intercropping, crop descriptions | Rules and dictionaries |
| ROI and cost estimates | Formulas and fixed assumptions, not learned yield |
| Login, three free daily analyses, premium demo code, history | Account/business logic |

Do not attribute fertilizer advice or ROI to SHAP. The explanation accounts for
the model score only. The existing “confidence” label means model class
probability, not independently calibrated confidence in farm suitability.

## Run and demonstrate it

Live app: <https://owaruurawo-luntiai-crop-model.hf.space/app/>

Source: <https://github.com/joseph-alejo/LuntiAI>

Space source: <https://huggingface.co/spaces/owaruurawo/luntiai-crop-model/tree/main>

On this computer, use `D:\XAI\LuntiAI` and run `./start-local.ps1` in PowerShell.
Then open <http://127.0.0.1:8000/app/>. For a fresh checkout, create a Python 3.11
environment and install `requirements.txt`; use `requirements-notebook.txt`
for notebook tools too. The saved model requires scikit-learn 1.8.0; the study
uses SHAP 0.45.0. An OpenWeatherMap key is optional. Never commit keys or runtime
account databases. Demo accounts are ephemeral on the hosted container.

Demonstration sequence:

1. Create a disposable alias account; choose Madaum and show the labeled presets.
2. Show the eight input values, explain their units, and submit a recommendation.
3. Explain the crop score, baseline, all eight signed terms, and runner-up gap.
4. Open the notebook's confusion matrix and local/global plots.
5. State the synthetic-data limitation and the excluded interventional experiment.

Verification commands, from the repository root in the activated environment:

```powershell
python -m pytest tests -q
python tests/smoke_deployment.py http://127.0.0.1:8000 --require-xai
```

The smoke check uses and removes its own disposable account. It checks model
readiness, login, invalid-input rejection, quota behavior, full XAI
reconstruction, demo premium redemption, and history.
